# 2026-11-12 동적 바쁜대기와 예제 관측 기록

이번 작업의 사실 후보 24개 중 프로젝트와 Go 런타임 소스에서 명확히 확인할 수 있는 16개를 제외했습니다. 남은 8개를 F34–F41로 기록합니다. 제외한 구현 설명은 이 문서에 다시 나열하지 않습니다. 아래의 실행 조건과 파일 식별값은 관측 결과의 적용 범위를 밝히기 위한 근거입니다.

기존 F01–F33과 별개의 작업 기록입니다. 과거 벤치마크, 이번 기능 검사, 사용자가 제공한 두 실행의 로그를 하나의 반복 측정으로 합치지 않습니다.

### F34. 사용자는 10초 간격 예약을 검토한 뒤 동적 대기 개선안의 적용을 요청했습니다

사용자는 10초 간격의 시각을 연이어 등록하는 상황을 질문한 뒤, `spinWindow`를 동적으로 처리하는 방법을 요청했습니다. 예제 코드를 먼저 확인하고 동일 시각 등록의 동작까지 설명받은 후, 직접 파일 수정을 요청했습니다.

이 선택은 이 프로젝트의 연속 예약에서 바쁜대기 중첩을 줄이기 위한 변경의 배경입니다. 이전의 1분 설정을 모든 알람이 항상 1분씩 바쁜대기해야 한다는 요구로 해석하지 않습니다. 여러 작업자의 빠른 실행 재개를 우선한 기존 F31의 맥락도 함께 참고합니다.

근거: 이번 대화의 동적 처리 질문, 코드 제시 요청, 동일 시각 질문, 적용 요청.

### F35. 사용자는 예제의 마이크로초 표시와 기록 후 일괄 출력을 요청했습니다

사용자는 예제 시각을 마이크로초까지 표시하도록 요청했습니다. 작업자별 시각 차이를 확인한 뒤에는 수신 직후 시각만 저장하고 모두 기록을 마친 뒤 출력하도록 수정해 달라고 명시했습니다.

이는 현재 예제의 관측 방식에 관한 사용자 선택입니다. 표시 자릿수 변경이나 출력 분리의 적용 자체를 실행 시점의 마이크로초 정확도 보장으로 해석하지 않습니다.

근거: 예제 시각 표시 수정 요청과 수신 시각 기록 후 출력 수정 요청.

### F36. 임시 검증에서 삽입 후 대기 상태 전환과 경쟁 상태 검사가 성공했습니다

Go 1.26.5, darwin/arm64의 임시 모듈에서 기존 검사와 추가 검사 4개를 실행했습니다. 추가 검사는 순서가 뒤섞인 등록, 서로 다른 목표 시각의 동시 등록, 바쁜대기 중 삽입, 수면 중 삽입을 다뤘습니다.

대기 상태 검사 두 개는 각각 목표까지 900ms인 실제 시계를 사용했습니다. `runtime.Stack`에서 작업자의 수면 상태를 확인한 결과는 다음과 같습니다.

| 검사 | 관측한 작업자 상태 |
|---|---|
| 바쁜대기 중 더 이른 알람 삽입 | 삽입 전 수면 0개·그 외 4개에서, 삽입 후 수면 4개·그 외 4개로 전환됐습니다. |
| 수면 중 더 이른 알람 삽입 | 삽입 전 수면 4개를 확인했고, 기존 바쁜대기 시작 예정 시각이 지난 뒤에도 수면 4개·그 외 4개를 확인했습니다. |

그 외는 스택 헤더가 수면 상태가 아닌 작업자 수입니다. 동시에 CPU에서 실행 중인 개수나 CPU 사용률을 측정한 값이 아닙니다.

임시 모듈에서 `go test -v ./...`와 `go test -race -count=3 -cpu=1,4,14 ./...`가 성공했습니다. 이 상태 관측 검사는 임시 디렉터리에서 수행했으며 프로젝트의 영구 회귀 검사와 구분합니다. 짧은 시간 조건의 기능 검사이므로 1분 바쁜대기의 비용이나 지연 상한을 입증하지 않습니다.

근거: `/tmp/alarmclock-dynamic-preview.V5OC35/`의 당시 실행 결과. 임시 파일의 계속된 존재는 전제하지 않습니다.

### F37. 프로젝트 적용 후 빌드·정적 검사·반복 경쟁 상태 검사가 성공했습니다

동적 대기 구현을 실제 프로젝트에 적용한 뒤 다음 명령이 모두 성공했습니다.

- `go build ./...`
- `go vet ./...`
- `go test -race -count=3 -cpu=1,4,14 ./...`
- `git diff --check`

기존 검사에 더해 순서가 뒤섞인 등록, 동일 시각 재등록 시 구간 유지와 채널 재사용, 서로 다른 시각의 동시 등록을 검사했습니다. 이때의 `-cpu` 값은 검사에 사용한 GOMAXPROCS 설정이며 물리 코어 수가 아닙니다.

검증한 소스를 식별하는 SHA-256은 다음과 같습니다. 이번 기록 시점에 파일 내용을 확인했으며, 검증 이후 해당 파일에 추가 변경은 없었습니다.

| 파일 | SHA-256 |
|---|---|
| `alarmclock.go` | `bec87cd4753512e7f63cf884ea837f81e54b99cf8b2fb6cb1ee5763717afc0dc` |
| `alarmclock_dynamic_test.go` | `2f7805fea1feef8f7eaccb695b0ac7a0a88a9eda189263be4af3b5cc1df99f48` |

이는 해당 검사에서 오류가 검출되지 않았다는 결과입니다. 모든 실행 순서의 무오류 증명이나 성능 측정은 아닙니다.

근거: 이번 대화에서 프로젝트 적용 직후 실행한 명령의 종료 코드와 출력, 기록 시점의 파일 해시.

### F38. 일괄 출력 예제의 실제 실행에서 작업자 24개가 완료됐습니다

기록 후 일괄 출력하도록 수정한 예제를 `go run -race ./cmd/example`로 실행했습니다. 10·20·30초 뒤 알람에 각각 작업자 8개를 등록한 실제 실행에서 총 24개 기록이 출력됐고, 종료 코드 0으로 완료되며 race 오류가 검출되지 않았습니다. `go vet ./cmd/example`도 성공했습니다.

검증한 `cmd/example/main.go`의 SHA-256은 `9d37bfc0946798356511e61730fbe765a4e2b5044cef9d417c360533cc7edd5c`입니다. 기록 시점에 해시를 확인했으며, 실행 검증 이후 파일의 추가 변경은 없었습니다.

이 실행에는 race 계측이 포함됐습니다. 여기서 나온 시각을 사용자가 제공한 실행의 성능 표본과 합치거나, race 계측 없이 반복 측정한 지연 분포로 설명하지 않습니다.

근거: 이번 대화의 일괄 출력 수정 후 실행 결과와 파일 해시.

### F39. 사용자의 즉시 출력 표본에서 작업자 간 표시 시각 범위는 14µs였습니다

사용자가 마이크로초 표시로 실행한 뒤 제공한 첫 번째 알람의 출력입니다. 실행 명령은 `go run main.go`로 제시됐습니다. 각 작업자가 수신 후 바로 출력하던 단계이며, 제공된 표본은 첫 알람의 작업자 8개 기록 한 묶음입니다.

| Worker | 표시 시각 |
|---|---|
| 1 | 04:05:29.353902 |
| 2 | 04:05:29.353899 |
| 3 | 04:05:29.353889 |
| 4 | 04:05:29.353889 |
| 5 | 04:05:29.353889 |
| 6 | 04:05:29.353903 |
| 7 | 04:05:29.353902 |
| 8 | 04:05:29.353900 |

표시 시각의 최솟값은 `.353889`, 최댓값은 `.353903`이므로 범위는 14µs입니다. worker 1과 5의 표시 시각 차이는 13µs였습니다. 이는 목표 대비 지연이나 터미널에 줄이 나타난 시각의 차이를 측정한 값이 아닙니다.

근거: 사용자가 대화에 직접 붙여 넣은 첫 번째 실행 출력. 표는 작업자 번호순으로 재배열했습니다.

### F40. 일괄 출력 후 사용자 표본에는 9µs 차이와 worker 1·5의 지연이 남았습니다

사용자가 기록 후 일괄 출력하는 변경을 적용한 뒤 `go run main.go`의 결과로 제공한 첫 알람의 기록입니다. 이 방식에서도 제공된 표본은 작업자 8개 기록 한 묶음입니다.

| Worker | 표시 시각 |
|---|---|
| 1 | 04:10:27.575741 |
| 2 | 04:10:27.575733 |
| 3 | 04:10:27.575733 |
| 4 | 04:10:27.575734 |
| 5 | 04:10:27.575742 |
| 6 | 04:10:27.575734 |
| 7 | 04:10:27.575734 |
| 8 | 04:10:27.575733 |

최솟값 `.575733`과 최댓값 `.575742`의 차이는 9µs입니다. worker 1·5는 가장 이른 기록보다 각각 8µs·9µs 늦었고, 나머지 6개는 `.575733` 또는 `.575734`에 모였습니다. 함께 늦은 작업자가 있었다는 관측이며, 특정 채널이나 CPU의 지연 원인을 확정한 결과는 아닙니다.

근거: 사용자가 대화에 직접 붙여 넣은 일괄 출력 변경 후 실행 출력.

### F41. 이번 관측으로 출력 분리의 성능 효과와 지연 원인을 확정하지 못했습니다

F39와 F40은 서로 다른 실행에서 제공된 각 한 묶음의 표본입니다. 호스트 부하를 통제하거나 조건 순서를 바꿔 반복한 비교가 아니므로 14µs에서 9µs로 성능이 개선됐다고 확정하지 않습니다. 사용자 실행의 상세 Go 버전, GOMAXPROCS, GC 상태와 CPU 배치는 별도로 수집하지 않았습니다.

제공된 두 로그는 수신 후 기록한 시각의 소수점 6자리 벽시계 문자열입니다. 목표 시각과 단조 시계 차이, 채널별 `close` 직전·직후 시각, 스케줄러 추적은 기록되지 않았으므로 목표 대비 지연과 채널 닫기·수신자 실행 재개 지연을 분해할 수 없었습니다.

채널을 닫는 고루틴의 지연, 수신자 스케줄링, 다음 알람의 바쁜대기와의 경쟁은 대화에서 제시한 원인 후보였습니다. 이번 실행에서 원인별 영향을 분리하는 측정은 하지 않았으므로 확인된 원인으로 기록하지 않습니다. 동적 대기 변경 전후의 CPU 비용이나 지연 분포를 비교하는 벤치마크도 수행하지 않았습니다.

근거: F36–F40의 실제 검증 범위와 사용자 제공 로그에 포함된 관측값.
