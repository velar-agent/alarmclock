# 측정 및 조사 기록

2026-11-02 작업 중 확인한 사실 중 현재 프로젝트 코드·설정만으로 바로 알 수 없는 12개를 기록합니다. 측정 환경은 macOS, darwin/arm64, Go 1.26.5이며 논리 CPU 수는 14개였습니다. 별도 부하를 추가하지 않았지만 호스트의 백그라운드 부하는 통제하지 않았습니다.

이 기록에는 이전 채널 방식, 독립적인 조건식 벤치마크, 루프 실험이 포함됩니다. 서로 다른 실험의 수치를 현재 분 정각 콜백 구현의 성능 분포로 합쳐 해석하지 않습니다. 아래에 조건과 핵심 수치를 보존했으므로 임시 측정 파일이 없어도 기록을 읽을 수 있습니다.

### F01. 이 환경의 벽시계 보고 해상도는 1µs였습니다

네이티브 `clock_getres(CLOCK_REALTIME)` 호출이 1,000ns를 반환했습니다. 관측한 벽시계 출력도 나노초 부분의 마지막 세 자리가 `000`이었습니다. 소수점 아홉 자리로 출력한다는 사실은 1ns 해상도나 실제 UTC와의 1ns 정확도를 의미하지 않습니다. 외부 기준 시계에 대한 오차는 측정하지 않았습니다.

### F02. 단조 시계에서는 41ns와 42ns 변화가 관측됐습니다

`mach_timebase_info`의 분자·분모는 125와 3으로, 틱당 약 41.6667ns였습니다. 단조 시계 정보를 가진 목표에 대해 `time.Until`을 2,000,000회 연속 읽었을 때 최소 양의 변화는 41ns였고, 41ns 변화 343,761회와 42ns 변화 687,244회가 관측됐습니다. 값이 같았던 경우는 960,020회였습니다. 이 수치를 F01의 벽시계 해상도와 혼동하지 않습니다.

측정 원본: `alarm-clock-resolution.5YA7dq/results.json`. Mach 시간 단위의 환산 방식은 [Apple 문서](https://developer.apple.com/library/archive/qa/qa1398/_index.html), Go의 Darwin ARM64 시계 구현은 [Go 1.26.5 소스](https://github.com/golang/go/blob/go1.26.5/src/runtime/sys_darwin_arm64.s)를 참고합니다.

### F03. 분 정각 실행에서 0ns가 측정됐지만 실제 오차 0은 입증되지 않았습니다

사용자가 제공한 한 실행에서 시작 시각은 `2026-11-02 07:32:27.971795000 +09:00`, 목표와 기록된 콜백 진입 시각은 모두 `07:33:00.000000000 +09:00`이었고, 경과 시간은 32.028205초, 기록된 지연은 0ns였습니다.

이 실행의 측정값을 0ns라고 표현할 수 있습니다. 다만 F01의 해상도에서 같은 벽시계 눈금으로 기록됐다는 의미이며, 실제 오차가 정확히 0이거나 이후 실행에도 같은 결과가 나온다는 증거는 아닙니다. 단일 실행으로 p99나 최대 지연의 상한을 정하지 않습니다.

### F04. 시계 기준 혼용으로 표시 시각과 계산한 지연이 달랐습니다

이전 실행에서 벽시계 출력의 목표는 `07:26:00.000000000 +09:00`, 실행 시각은 `07:26:00.149470000 +09:00`이었지만 지연 출력은 500ns였습니다. 표시 시각끼리의 차이는 149.470ms였고, 단조 시계 정보를 유지한 값끼리 계산한 차이는 500ns였습니다.

이 사례는 표시와 지연 계산의 시계 기준을 함께 확인해야 하는 이유입니다. 두 시계가 벌어진 원인은 진단하지 않았으므로 NTP나 특정 운영체제 동작을 원인으로 단정하지 않습니다. Go의 단조 시계 사용 조건과 제거 방법은 [Go 1.26.5 time 문서](https://pkg.go.dev/time@go1.26.5#hdr-Monotonic_Clocks)를 참고합니다.

측정 원본: `alarm-clock-callback.WXIgEx/minute-output.txt`.

### F05. 단조 시계 입력에서는 Until 조건식이 Now와 Before 조합보다 빨랐습니다

1시간 뒤 목표에 단조 시계 정보를 유지한 조건식 벤치마크에서 5회 실행의 ns/op 중앙값은 다음과 같았습니다.

| 조건식 | ns/op 중앙값 |
|---|---:|
| `time.Until(at) > 0` | 11.330 |
| `time.Since(at) < 0` | 11.250 |
| `time.Now().Before(at)` | 27.140 |
| `at.Sub(time.Now()) > 0` | 26.230 |

각 실행은 `-benchtime=200ms -count=5 -cpu=1` 조건으로 수행했고, 모두 0 B/op 및 0 allocs/op였습니다. 이 수치는 조건식 평가 비용이며 알람 실행 오차가 아닙니다. Until과 Since의 작은 차이는 실행별 범위가 겹쳤으므로 우열을 단정하지 않습니다.

측정 원본: `alarm-clock-condition.9SJ51W/results.txt`.

### F06. 벽시계 입력에서는 조건식 성능 순위가 달랐습니다

F05와 같은 방식에서 목표의 단조 시계 정보를 제거한 경우, 5회 실행의 중앙값은 다음과 같았습니다.

| 조건식 | ns/op 중앙값 |
|---|---:|
| `time.Until(at) > 0` | 30.690 |
| `time.Since(at) < 0` | 28.190 |
| `time.Now().Before(at)` | 25.970 |
| `at.Sub(time.Now()) > 0` | 29.820 |

따라서 단조 시계 입력의 결과만으로 Until을 모든 상황에서 가장 빠른 조건식이라고 말할 수 없습니다. 실제 목표 시각이 사용하는 시계 기준으로 비교해야 합니다.

측정 원본: `alarm-clock-condition.9SJ51W/results.txt`.

### F07. 타이머가 전달한 시각은 실제 수신 지연을 작게 보이게 했습니다

이전 `time.After` 기반 채널 방식에서 채널이 전달한 시각으로 계산한 지연의 p99는 11.458µs였지만, 수신 직후 새로 읽은 시각으로 계산한 지연의 p99는 735µs였습니다. 실제 수신 직후 지연의 중앙값은 644.583µs, 최대는 4.350375ms였습니다.

F07–F09 실험은 방식별 1,500회, 워밍업 50회, 각 목표는 5ms 뒤, GOMAXPROCS 14 조건이었고 매 표본마다 방식 실행 순서를 순환했습니다. Go 타이머의 전달 시각 보정은 [Go 1.26.5 sendTime 구현](https://github.com/golang/go/blob/go1.26.5/src/time/sleep.go)에서도 확인했습니다. 실제 수신·작업 시작 지연을 평가할 때 타이머가 전달한 시각으로 대신하지 않습니다.

측정 원본: `alarm-clock-precision.c6F5cu/results.json`.

### F08. 1ms 미리 깨우는 방식에서도 1ms 이상의 지연이 나왔습니다

목표 1ms 전에 Sleep을 끝내고 바쁜대기 후 채널로 전달한 방식에서, 실제 수신 지연의 중앙값은 3µs, p99는 36µs, 최대는 3.441875ms였습니다. 1,500회 중 6회가 1ms 넘게 늦었습니다.

따라서 이 실험은 1ms 사전 기상만으로 지연 상한을 보장할 수 있다는 주장을 뒷받침하지 않습니다. 측정 조건은 F07과 같으며, 5ms 뒤 목표로 수행한 결과를 장시간 예약이나 1분 스핀의 결과로 확대하지 않습니다.

측정 원본: `alarm-clock-precision.c6F5cu/results.json`.

### F09. 같은 고루틴에서 바로 관측하면 중앙값은 줄었지만 최대 지연 개선은 확인되지 않았습니다

F08의 채널 방식과, 호출한 고루틴에서 기다린 뒤 즉시 시각을 관측한 직접 대기 방식을 비교했습니다. 둘 다 목표 1ms 전까지 Sleep한 뒤 바쁜대기했습니다.

| 관측 방식 | 중앙값 | p99 | 관측 최대 |
|---|---:|---:|---:|
| 채널 수신 직후 | 3µs | 36µs | 3.441875ms |
| 같은 고루틴에서 대기 직후 | 0.166µs | 27.417µs | 3.5485ms |

이 실험에서는 직접 대기의 중앙값과 p99가 더 작았지만 최대값은 더 컸습니다. 직접 대기 실험은 호출자를 블록하는 별도 구현이었으므로, 이 수치를 현재 비동기 콜백 구현의 실측값으로 소개하지 않습니다.

측정 조건과 원본은 F07과 같습니다.

### F10. 순수 바쁜대기 실험의 중앙값 41ns와 최대 1.293875ms는 함께 관측된 값입니다

단조 시계로 1ms 뒤 목표를 잡고, 바쁜대기 루프 종료 직후 새 시각을 읽었습니다. 워밍업 100회, 측정 5,000회, GOMAXPROCS 14 조건에서 지연 중앙값은 41ns, p99는 2.792µs, 관측 최대는 1.293875ms였습니다. 1µs 초과는 79회, 1ms 초과는 2회였으며 목표 이전 관측은 없었습니다.

이 실험은 채널 전달과 콘솔 출력을 포함하지 않았습니다. 중앙값이 작아도 드문 큰 지연이 있을 수 있다는 관측이며, 분 정각 벽시계 알람이나 현재 콜백 구현의 분포를 측정한 결과는 아닙니다.

측정 원본: `alarm-clock-resolution.5YA7dq/results.json`.

### F11. 1분 스핀은 한 실행에서 약 60 CPU초를 소비했습니다

이전 채널 구현으로 61초 뒤를 예약하고 약 1초 Sleep 뒤 1분 스핀을 수행했습니다. 프로세스 전체의 사용자·시스템 CPU 시간을 합한 값은 59.912727초였고, 총 경과 시간은 61.000007208초, 관측 지연은 7.208µs였습니다. CPU 시간은 `Getrusage(RUSAGE_SELF)`로 측정했습니다.

이 단일 실행은 약 한 코어를 1분 사용하는 수준의 비용이 관측됐다는 기록입니다. 특정 코어에 고정됐다는 뜻은 아니며, 더 짧은 스핀보다 정밀도가 좋다거나 최대 지연이 7.208µs로 제한된다는 증거도 아닙니다.

측정 근거: 당시 `minutecheck` 실행 출력. 지연과 CPU 비용을 함께 비교할 때 참고합니다.

### F12. synctest의 가짜 시간은 바쁜대기 때문에 진행하지 못할 수 있습니다

[testing/synctest 공식 문서](https://pkg.go.dev/testing/synctest#hdr-Time)에 따르면 버블 안의 모든 고루틴이 지속적으로 블록된 상태일 때 가짜 시간이 진행합니다. 계속 실행 가능한 바쁜대기 루프가 있으면 이 조건을 충족하지 못해, 가짜 시계의 미래 목표에 도달하지 못할 수 있습니다.

이는 문서에서 확인한 테스트 환경 특성으로, 실제로 테스트를 멈춰서 얻은 실측 결과는 아닙니다. 가짜 시간을 사용하는 테스트에서 실제 바쁜대기 루프를 그대로 실행할 수 있다고 가정하지 않습니다.
