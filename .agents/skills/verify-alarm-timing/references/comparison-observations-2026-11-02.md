# 2026-11-02 비교 실행과 검증 기록

이번 대화에서 추가로 확인한 사실 중 현재 프로젝트 코드만으로 알 수 없는 7개를 F13–F19로 기록합니다. 기존 F01–F12는 별도 환경과 실험의 기록이므로 합쳐 집계하지 않습니다. 아래 수치와 검증 범위는 2026-11-02 작업 당시의 도구 실행 출력에 근거합니다.

### F13. 이번 환경 출력은 Apple M2·논리 CPU 8개·Go 1.27.2였습니다

20:33 및 20:45 비교 실행에서 다음 값이 출력됐습니다. 시각은 모두 KST입니다.

| 항목 | 관측값 |
|---|---|
| OS / 아키텍처 | darwin/arm64 |
| OS 버전 | macOS 27.0.1, build 26A434 |
| CPU 모델 | Apple M2 |
| Go에서 보고한 논리 CPU 수 | 8 |
| GOMAXPROCS | 8 |
| Go 버전 | go1.27.2 |
| 컴파일러 | gc |

기존 F01–F12에는 Go 1.26.5와 논리 CPU 14개가 기록되어 있습니다. 두 환경 기록의 차이가 생긴 원인은 조사하지 않았습니다. 과거 환경을 이번 실행의 환경으로 대입하지 않습니다. 환경 출력을 추가하기 전의 세 비교 실행에는 이 전체 환경 정보가 함께 기록되지 않았습니다.

### F14. 다섯 번의 정분 비교에서 실행 지연이 다르게 관측됐습니다

각 행은 같은 프로세스에서 두 방식을 같은 정분에 예약한 단일 실행입니다. 목표와 지연은 벽시계 기준이며, 바쁜대기는 콜백 진입 직후, `time.After`는 채널 수신 직후 새로 읽은 시각을 사용했습니다. 각 방식의 출력은 측정 이후에 수행했습니다.

| 목표 시각(KST) | 시작부터 목표까지 | 카운터 조건 | 바쁜대기 지연 | time.After 지연 | 지연 차이 |
|---|---|---|---:|---:|---:|
| 20:20:00 | 36.230909초 | 카운터 없음 | 1µs | 847µs | 846µs |
| 20:23:00 | 37.842131초 | 카운터 없음 | 6µs | 1.135ms | 1.129ms |
| 20:26:00 | 57.472104초 | 경과 초와 Now 출력 | 0µs | 1.116ms | 1.116ms |
| 20:33:00 | 0.175035초 | 경과 초만 출력 | 9µs | 18µs | 9µs |
| 20:45:00 | 57.291307초 | 경과 초만 출력 | 0µs | 1.147ms | 1.147ms |

지연 차이는 `time.After` 지연에서 바쁜대기 지연을 뺀 값입니다. 다섯 실행 모두 바쁜대기 구간이 1분이던 구현을 사용했으며, 이 값이 인스턴스 필드로 옮겨지기 전의 실측입니다. 20:45 실행은 패키지 이동 후, 생성자 이름을 단축하기 전의 스크래치패드 복사본이었습니다.

대기 길이와 출력 조건이 달랐고 호스트의 백그라운드 부하는 통제하지 않았습니다. 이 표로 카운터 유무의 효과나 반복 실험의 p99, 지연 상한을 주장하지 않습니다. 이 다섯 실행에서는 CPU 시간을 별도로 측정하지 않았습니다. 기록된 0µs의 해석은 기존 F03을 따릅니다.

실행 파일은 작업 당시 `/tmp/alarm-clock-compare.pk49Tl`, `/tmp/alarm-clock-environment.cevfrq`, `/tmp/alarmclock-rename.ZmmHqk`에서 준비했습니다. 임시 파일의 지속적인 존재를 전제로 하지 않도록 핵심 조건과 수치를 이 표에 보존합니다.

### F15. 결과 출력은 목표보다 193µs에서 1.182ms 늦게 시작됐습니다

F14와 같은 다섯 실행에서 기록한 결과 출력 시작 시각입니다. 알람 실행 지연과 다른 관측 지점입니다.

| 출력 목표(KST) | Compared at(KST) | 목표 대비 지연 |
|---|---|---:|
| 20:20:01 | 20:20:01.001138 | 1.138ms |
| 20:23:01 | 20:23:01.001182 | 1.182ms |
| 20:26:01 | 20:26:01.001150 | 1.150ms |
| 20:33:01 | 20:33:01.001043 | 1.043ms |

앞의 두 실행은 Sleep으로 출력 시점을 기다렸고, 뒤의 세 실행은 카운터와 출력 타이머를 함께 기다렸습니다. 이 값은 출력 시작 전에 읽은 시각이며 터미널에 모든 문자가 표시된 시각은 측정하지 않았습니다. 관측 범위가 향후 출력 지연의 상한을 의미하지는 않습니다.

### F16. Linux와 Windows는 amd64 크로스 빌드까지만 확인했습니다

환경 정보 출력을 추가한 뒤 macOS에서 실제 실행했고, Linux/amd64와 Windows/amd64 대상으로 각각 빌드에 성공했습니다. 이 크로스 빌드는 모듈 경로와 패키지 구조를 바꾸기 전의 소스에 대한 결과입니다.

Linux와 Windows 호스트에서 프로그램을 실행하지 않았으므로 해당 OS의 CPU·OS 조회 명령 실행, 권한, 조회 시간 제한 내 완료 여부까지 검증한 것은 아닙니다. 플랫폼 분기가 소스에 존재하거나 빌드가 성공했다는 근거만으로 실제 환경 조회 성공을 단정하지 않습니다.

### F17. 새 import 경로와 생성자는 로컬 대체 모듈로 실행 검증했습니다

모듈 이동과 생성자 이름 변경 후 README의 2초 알람 예제를 별도 임시 모듈에서 실행해 정상 종료를 확인했습니다. 임시 모듈은 `replace`로 새 모듈 경로를 로컬 프로젝트 복사본에 연결했습니다.

이 검증은 외부 패키지에서 새 경로와 API를 사용해 빌드하고 콜백을 실행할 수 있다는 근거입니다. GitHub에서 모듈을 내려받는 검증은 수행하지 않았으므로 원격 배포·태그·모듈 프록시 가용성의 근거로 사용하지 않습니다. 해당 2초 실행은 벽시계 정분 비교 표의 추가 표본으로 합치지 않습니다.

### F18. spinWindow 필드 이동 직후에는 빌드와 정적 검사만 수행했습니다

바쁜대기 구간을 인스턴스 필드로 옮긴 수정 후 `go build ./...`와 `go vet ./...`가 성공했습니다. 그 수정 뒤에는 정분 비교 실행이나 CPU 시간 측정을 다시 수행하지 않았습니다.

F14–F15의 실측과 F17의 예제 실행은 그 수정 전의 기록입니다. 변경 후의 정밀도를 실측했다고 설명할 때는 새 실행의 근거가 필요합니다.

### F19. 논리 CPU 수와 GOMAXPROCS는 의미와 갱신 시점이 다릅니다

Go 1.27.2의 로컬 공식 문서에서 다음 내용을 확인했습니다.

- `runtime.NumCPU`는 프로세스가 사용할 수 있는 논리 CPU 수이며, 시작할 때 조사한 값입니다. 시작 후 OS의 CPU 할당 변경은 반영하지 않습니다.
- `runtime.GOMAXPROCS(0)`은 설정을 바꾸지 않고 현재 동시 실행 한도를 읽습니다. 기본값에는 논리 CPU 수, CPU affinity, Linux cgroup CPU 제한 등이 영향을 줄 수 있습니다.
- Go 런타임이 기본값을 자동 갱신할 수 있지만, 환경 변수나 명시적인 설정으로 자동 갱신이 비활성화될 수 있습니다.

따라서 출력된 두 값이 같아도 물리 코어 수를 뜻하지는 않습니다. 결과 출력 시점에 읽은 GOMAXPROCS만으로 대기 구간 내내 같은 값이었다고 입증할 수도 없습니다.

근거: 작업 중 실행한 `go doc runtime.NumCPU`와 `go doc runtime.GOMAXPROCS`, 공식 [NumCPU 문서](https://pkg.go.dev/runtime@go1.27.2#NumCPU)와 [GOMAXPROCS 문서](https://pkg.go.dev/runtime@go1.27.2#GOMAXPROCS).
