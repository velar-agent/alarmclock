# 2026-11-12 고루틴 깨우기와 바쁜대기 기록

이번 작업에서 사실 후보 26개를 나열하고, 코드에서 명확히 확인되는 런타임 동작과 프로젝트 구현 12개를 제외했습니다. 남은 14개를 F20–F33으로 기록합니다. 기존 F01–F19의 실측과 다른 실험이며, 과거 수치를 이번 실행의 표본으로 합치지 않습니다.

## 실험 조건과 관측 지점

아래 조건은 수치 해석에 필요한 실행 맥락입니다. 코드의 API나 제어 흐름 자체를 별도 사실로 다시 기록하지 않습니다.

| 실험 | 실행 범위 | 반복과 시계 기준 | 시작 지연의 기준점 |
|---|---|---|---|
| A: 채널 분산, 후속 계산 없음 | 대기자 100·1,000·10,000개, GOMAXPROCS 1·4·14, 단일 채널 및 2·4·8·16채널의 순차·병렬 닫기 | 최초 구성별 30회, 워밍업 3회. 대기자 1,000·10,000개/GOMAXPROCS 4·14는 실행 순서를 바꿔 50회 추가, 워밍업 3회. 단조 시계 기준 | 단일 또는 순차 닫기는 최초 `close` 직전, 병렬 닫기는 공통 시작 신호 직전부터 각 수신자가 대기를 통과해 시각을 기록할 때까지 |
| B: 깨어난 뒤 CPU 계산 | 대기자 1,000·10,000개, GOMAXPROCS 4·14, A와 같은 채널 구성. 각 작업자는 시작 시각 기록 후 xorshift 정수 연산 루프 10,000회 수행 | 구성별 20회, 워밍업 2회. 단조 시계 기준 | A와 같으며 작업 완료가 아닌 작업 시작을 관측 |
| C: 직접 바쁜대기 비교 | 대기자 1,000개, 채널 4개, GOMAXPROCS 1·4·14, 목표까지 30ms. 바쁜대기 1개와 중간 신호를 쓰는 방식 대 바쁜대기 4개가 직접 닫는 방식 | 방식·GOMAXPROCS 조합별 40회, 워밍업 3회. 목표와 수신 시각 모두 벽시계 기준 | 목표 시각부터 각 수신자가 대기를 통과해 시각을 기록할 때까지 |

A는 최초 2,430회와 추가 1,800회, B는 720회로 합계 4,950회였습니다. C는 별도 240회였습니다. 워밍업은 이 횟수에 포함하지 않았습니다. 아래 표의 값은 별도 표시가 없으면 각 시행에서 관측한 지표의 중앙값입니다. '시작 간격'은 각 시행의 마지막 시작 시각에서 첫 시작 시각을 뺀 값의 중앙값이며, 각 시각의 중앙값끼리 뺀 값이 아닙니다.

측정 전에 고루틴 프로파일로 수신 대기를 확인했고, 고루틴 생성은 측정 구간에서 제외했습니다. 자동 GC를 끄고 표본마다 측정 전에 명시적으로 GC를 수행했으며, 대기 확인 후 2ms 쉬었습니다. 작업자는 개별 기록 공간과 해제 채널을 사용했고 공유 완료 WaitGroup은 측정 후 정리에 사용했습니다. 조건 실행 순서를 각 라운드에서 섞었습니다. 성능 측정에는 race 계측을 사용하지 않았습니다.

프로파일 수집·사전 GC의 캐시 영향, 시각 읽기·기록·후속 대기의 비용은 존재합니다. 호스트 백그라운드 부하와 CPU affinity는 통제하지 않았습니다. A·B에서는 CPU 사용률을 측정하지 않았습니다.

### F20. 이번 측정 환경은 M4 Max·논리 CPU 14개·Go 1.26.5였습니다

실행 환경은 macOS/darwin/arm64, Apple M4 Max, Go 1.26.5였습니다. `sysctl`과 런타임 조회에서 논리 CPU 14개를 확인했습니다. 각 실험의 GOMAXPROCS는 표의 값으로 명시적으로 설정했습니다. 이 기록은 F13의 M2·Go 1.27.2 환경과 다릅니다. 두 환경의 차이를 성능 차이의 원인으로 단정하지 않습니다.

근거: 작업 중 `go version`, `sysctl` 출력과 실험 메타데이터.

### F24. 여러 채널을 순차로 닫으면 더 느려지는 경우가 있었습니다

실험 A, 대기자 10,000개, GOMAXPROCS 14, 구성별 80회에서 마지막 시작까지의 중앙값은 단일 채널 1,085.000µs, 4채널 순차 닫기 1,304.500µs였습니다. 채널을 나누는 것만으로 속도가 개선된다고 판단할 수 없습니다.

### F25. GOMAXPROCS 1에서는 병렬 닫기를 구성해도 분산이 더 느렸습니다

실험 A, 대기자 10,000개, 구성별 30회에서 마지막 시작까지의 중앙값은 단일 채널 1,468.188µs, 4채널 병렬 구성 1,767.312µs였습니다. 여러 알림 고루틴을 만드는 효과를 실제로 병렬 실행할 수 있는 조건의 결과와 구분합니다.

### F26. GOMAXPROCS가 더 큰 설정에서도 깨우기가 느려질 수 있었습니다

실험 A, 대기자 10,000개, 단일 채널, 설정별 80회에서 마지막 시작까지의 중앙값은 GOMAXPROCS 4에서 784.480µs, 14에서 1,085.000µs였습니다. 원인은 별도로 진단하지 않았으므로 스케줄러 경합, CPU 종류, OS 스케줄링 중 하나를 확정 원인으로 기록하지 않습니다.

| 구성 | 모든 닫기 호출이 반환할 때까지 | 마지막 수신자 시작까지 |
|---|---:|---:|

두 지표는 같은 최초 신호 시각을 기준으로 측정했습니다. 닫기 완료 지연만을 사용자 작업의 실행 재개 속도로 대체해서 해석하지 않습니다.

### F28. 깨어난 뒤 CPU 계산을 추가하자 채널 분산의 이점이 거의 사라졌습니다

실험 B, 대기자 10,000개, GOMAXPROCS 14, 구성별 20회에서 마지막 시작까지의 중앙값은 단일 채널 13.392376ms, 16채널 병렬 13.393021ms였습니다. 이는 작업 완료 시각이 아니라 마지막 작업자의 시작 시각입니다.

먼저 깨어난 작업자에게도 동일한 CPU 계산을 수행시킨 결과입니다. 이 합성 부하를 실제 네트워크 I/O나 사용자의 실제 작업에 대한 측정으로 확대하지 않습니다.

### F29. 직접 바쁜대기 4개는 한 조건에서 CPU 비용 약 4배로 시작 지연을 약 36% 줄였습니다

실험 C, GOMAXPROCS 14, 방식별 40회 결과입니다.

| 방식 | 첫 시작 지연 | 마지막 시작 지연 | 시작 간격 | 프로세스 CPU 시간 |
|---|---:|---:|---:|---:|
| 바쁜대기 1개 + 중간 신호 | 24µs | 112µs | 88µs | 30.728ms |
| 직접 바쁜대기 4개 | 15µs | 72µs | 55µs | 120.828ms |

CPU 시간은 `Getrusage(RUSAGE_SELF)`의 사용자·시스템 시간 합계를 사용했습니다. 대기 시작부터 모든 작업자가 기록을 마친 것을 확인할 때까지의 프로세스 CPU 비용이며, 초기 설정과 측정 후 해제 작업은 제외했습니다. 여러 CPU에서 소비한 시간의 합이므로 30ms 경과 시간보다 클 수 있습니다. CPU 사용률을 직접 샘플링한 값은 아닙니다.

### F30. 직접 바쁜대기 4개의 이득은 실행 병렬성에 따라 달랐습니다

실험 C의 나머지 조건이며 각 행은 방식별 40회 중앙값입니다.

| GOMAXPROCS | 방식 | 마지막 시작 지연 | 프로세스 CPU 시간 |
|---|---|---:|---:|
| 1 | 바쁜대기 1개 + 중간 신호 | 169.5µs | 30.1985ms |
| 1 | 직접 바쁜대기 4개 | 189.5µs | 30.217ms |
| 4 | 바쁜대기 1개 + 중간 신호 | 88µs | 30.3375ms |
| 4 | 직접 바쁜대기 4개 | 84µs | 120.270ms |

GOMAXPROCS 1에서는 오히려 느렸고, 4에서는 CPU 비용 증가에 비해 시작 지연 감소가 작았습니다. F29의 개선 비율을 CPU 자원이 다른 환경에 그대로 적용하지 않습니다.

### F31. 사용자는 CPU 절감보다 여러 고루틴의 빠른 실행 재개를 우선했습니다

사용자는 "동시에 빨리 깨어나도록 하는 것이 나의 목표야."라고 목표를 명시했습니다. 중간 `trigger`가 있는 안을 검토한 뒤 4개가 직접 바쁜대기할 수 있는지 물었습니다. CPU 비용 증가와 시작 지연을 비교한 결과를 제시한 뒤, 사용자는 직접 바쁜대기 코드의 제시와 적용을 요청했습니다.

이것은 이번 프로젝트의 설계 선택 배경입니다. CPU 사용량을 줄이기 위해 중간 신호를 추가했던 이전 제안을 반드시 유지해야 하는 요구사항으로 취급하지 않습니다. 모든 상황에서 CPU를 제한 없이 사용해도 된다는 일반적인 허가로 확대하지도 않습니다.

### F32. 적용 코드의 빌드·정적 검사·경쟁 상태 검사와 사용 예제 실행은 성공했습니다

적용 후 실제 프로젝트에서 다음 검사가 모두 성공했습니다.

- `go build ./...`
- `go vet ./...`
- `go test -race -count=3 -cpu=1,4,14 ./...`
- `git diff --check`

경쟁 상태 검사에서 동시 등록 1,000개, 채널 배분과 수신 재개, 서로 다른 목표·인스턴스, 이미 지난 목표와 정리 중 등록, 두 시계 기준의 실제 짧은 바쁜대기, Sleep 후 바쁜대기의 동작을 검증했습니다. 별도의 스크래치패드에서 작업자 8개의 사용 예제도 `go run -race`로 실행해 모두 시작 시각을 기록하는 것을 확인했습니다.

검사 당시 `alarmclock.go`의 SHA-256은 `b60f62802d50564108a1c81f39c02cafe212a696a3f151f44fa4c33b102020da`였습니다. 이는 해당 실행에서 오류가 검출되지 않았다는 결과이며, 모든 가능한 실행 순서의 무오류 증명은 아닙니다.

### F33. 이번 검증은 적용 후 정분 실행과 1분 바쁜대기의 성능 측정을 포함하지 않았습니다

프로젝트에 적용한 뒤 `cmd/compare`를 실제 정분까지 실행하지 않았고, 직접 바쁜대기 4개를 1분 동안 실행한 CPU 비용·시작 지연 분포도 측정하지 않았습니다. F29–F30은 독립 벤치마크의 30ms 실험이며, F32는 기능과 경쟁 상태 검증입니다.

이번 변경의 Linux·Windows 실제 실행이나 크로스 빌드도 수행하지 않았습니다. 이전 F16의 크로스 빌드 성공을 이번 소스의 검증으로 대체하지 않습니다. 어떤 측정에서도 실시간 지연의 보장 가능한 상한이나 외부 UTC 기준 정확도는 입증하지 않았습니다.
