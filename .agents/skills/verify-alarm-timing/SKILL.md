# 알람 정밀도 검증

이 프로젝트에서 이미 확인한 사실은 [측정 및 조사 기록](references/observations.md)의 F01–F12를 참고합니다. 정분 비교 프로그램의 추가 실측과 검증 범위는 [2026-11-02 비교 실행 기록](references/comparison-observations-2026-11-02.md)의 F13–F19를 참고합니다. 현재 코드에서 바로 읽을 수 있는 API 이름, 필드 초기값, 제어 흐름은 이 스킬에 중복 기록하지 않습니다.

## 측정과 해석

1. 목표 시각과 측정값이 벽시계 기준인지 단조 시계 기준인지 먼저 확인합니다. 분 정각처럼 달력상의 시각을 다룰 때는 조건식 속도만 보고 시계 기준을 바꾸지 않습니다. 해상도와 시계 기준 혼용 사례는 F01–F04를 참고합니다.
2. 조건식 실행 비용, 루프 종료 지연, 채널 수신 지연, 콜백 진입 지연을 구분합니다. 실제 실행 지연을 확인할 때는 해당 지점에서 시각을 기록하고 출력은 이후에 수행합니다. 비교 근거는 F05–F10을 참고합니다.
3. 단일 실행의 측정값과 반복 측정의 분포, 보장 가능한 상한을 구분해 설명합니다. `0 ns`는 기록된 시각의 차이가 0이라는 뜻이며, 실제 오차가 없다는 증거로 사용하지 않습니다.
4. 대기 구간을 바꿀 때는 실행 지연과 CPU 시간을 함께 확인합니다. F08과 F11의 서로 다른 실험을 근거로 1분 대기가 1ms 대기보다 정확하다고 단정하지 않습니다.
5. 바쁜대기를 가짜 시간으로 테스트하려면 F12의 시간 진행 조건을 먼저 확인합니다. 실제 루프 검증과 시간 계산 로직 검증을 구분하고, 가짜 시간이 저절로 목표까지 진행한다고 가정하지 않습니다.

## 비교 실행과 검증 범위

- 새 실행을 과거 기록과 비교할 때는 F13의 환경 차이와 F14의 실행 조건을 확인합니다. 대기 길이와 카운터 출력 조건이 다른 실행을 한 조건의 반복 표본으로 합치지 않습니다.
- 알람 실행 지연과 결과 출력 지연은 별도로 해석합니다. 출력 시각 자체를 평가할 때는 F15를 참고합니다.
- 다른 OS의 실행 가능성이나 새 import 경로의 배포 상태를 설명할 때는 F16–F18의 실제 검증 범위를 확인합니다. 크로스 빌드, 로컬 대체 모듈 실행, 빌드·정적 검사는 각기 다른 근거입니다.
- 환경 출력의 CPU 수를 해석할 때는 F19를 참고합니다. 논리 CPU 수와 Go의 동시 실행 한도를 물리 코어 수나 측정 내내 고정된 값으로 단정하지 않습니다.

## 기록의 범위

실측값은 해당 날짜·장비·Go 버전·측정 방식에서 얻은 과거 관측입니다. 다른 환경이나 변경된 구현의 성능 보장으로 사용하지 않습니다. 새 결과를 추가할 때는 표본 수, 시계 기준, 관측 지점, 실행 조건을 함께 남기고 실측과 문서에서 확인한 사실을 구분합니다.
